# VLESS_GUIDE.md — VLESS-Reality on a VPS: 3x-ui and/or TelegramHelper bot

Practical reference for TelegramHelper operators. **Key clarification up front:**

> 🟢 **There is only one web panel here — 3x-ui.** The TelegramHelper bot is a **Telegram interface**; it has **no web pages** and no "second panel". When this document says "bot stack", it means "Xray launched by the bot's deploy script directly on the host, without 3x-ui". This is an alternative to 3x-ui for operators who do not need a browser panel.

## 0. Quick Summary: What Is Actually Running

A VPS can have two VLESS backend variants but three familiar management interfaces:

| What was chosen at install time | What actually listens on 443/TCP | How to manage it |
| --- | --- | --- |
| **Legacy Xray** | `xray.service` + `/usr/local/etc/xray/config.json` | Bot: `/provision`, `/profiles`, `/my_profile`; file: `/opt/TelegramHelper/vless_config.json`; terminal: `python3 scripts/ssh/vless.py ...` |
| **3x-ui via the `x-ui` terminal menu** | `x-ui.service` with its own internal Xray | Terminal: `x-ui`; bot after `/xui_setup`; browser panel also available |
| **3x-ui via the browser panel** | same `x-ui.service` with its own internal Xray | Browser: `https://YOUR_VPS_IP:PANEL_PORT/WEB_PATH/`; bot after `/xui_setup`; `x-ui` terminal as a utility menu |

Important: **the `x-ui` terminal menu and the 3x-ui browser panel are not two separate VLESS instances**. They are two interfaces to the same `x-ui.service`. The legacy `xray.service`, on the other hand, is a completely separate setup with no panel.

To quickly determine which setup is running on a VPS:

```bash
command -v x-ui || command -v 3x-ui || true
systemctl status x-ui --no-pager || systemctl status 3x-ui --no-pager || true
systemctl status xray --no-pager || true
cd /opt/TelegramHelper && python3 scripts/ssh/vless.py list_clients
```

If `x-ui` / `3x-ui` and `x-ui.service` are not found but `xray.service` is running and `scripts/ssh/vless.py list_clients` shows clients, this is **legacy VLESS via the host Xray service**. After modifying clients in this setup, sync and restart Xray:

```bash
cd /opt/TelegramHelper
python3 scripts/sync_xray_config.py
xray -test -config /usr/local/etc/xray/config.json
systemctl restart xray
```

This document covers three typical configurations and how to set them up and verify them:

1. **3x-ui only (native)** — you have a browser panel; the bot plays no role in VLESS.
2. **Bot Xray only** — no 3x-ui; the bot brings up `xray.service` on the host; clients are managed via `/provision`, `/profiles`, `/my_profile`, while `/vless_*` commands remain manual admin tools.
3. **3x-ui + bot via `/xui_setup`** — the panel remains the single source of truth; the bot calls its REST API and provides a Telegram UI (create a client, deliver a QR code).

## 1. Purpose of This Document

On a single VPS you may have:

- **3x-ui** — `x-ui.service` (native on the host) **or** a Docker container `3x-ui`/`x-ui`. It uses its own Xray from `/usr/local/x-ui/` and stores clients in `/etc/x-ui/x-ui.db`. This is the "web panel".
- **TelegramHelper bot** in Docker (`telegram-helper-lite`). Optionally: in the "without 3x-ui" scenario, `deploy_fresh_vps.sh` installs a **native** `xray.service` on the host with config `/usr/local/etc/xray/config.json` and client records in `vless_config.json`. The bot then manages this Xray via `/provision`, `/profiles`, `/my_profile`, and the manual `/vless_*` commands. This is **not** a "second panel", just a different Xray instance.

A common misconception: *"One web panel (3x-ui) and a Telegram bot — so they share the same clients."* **No.** If both variants are running simultaneously on a server, they are two independent Xray processes with independent client lists; the Telegram bot does not route network traffic on its own.

## 2. Where Things Live

| | 3x-ui (web panel) | TelegramHelper bot + own Xray (without 3x-ui) |
| --- | --- | --- |
| **Xray binary** | `/usr/local/x-ui/bin/xray-linux-amd64`, started by x-ui | `xray.service` on the host (XTLS-install), binary at `/usr/local/bin/xray` |
| **Reality config** | Generated by the panel from its database | `/usr/local/etc/xray/config.json` |
| **Client list** | SQLite `/etc/x-ui/x-ui.db` | `vless_config.json` in the bot directory (`/opt/TelegramHelper`) |
| **Component location** | Native on host (`x-ui.service`) **or** Docker | Bot — Docker (`telegram-helper-lite`); Xray — native on host |
| **Operator interface** | **Browser:** `https://host:port/<web_base_path>/` + bot via `/xui_setup` | **Telegram:** `/provision`, `/profiles`, `/my_profile`, `/vless_*`, `/user` |
| **Profile delivery** | `/profiles`, `/my_profile`, `/email_profile` after `/xui_setup`, or **QR / URL** button in the panel | `/profiles`, `/my_profile`, `/email_profile`, `/vless_qr`, `/vless_export`, `/user` card |

**Summary:** in the browser, there is **one** real Xray management panel — **3x-ui**. The bot is a Telegram interface. If both `x-ui` and the bot's `xray.service` are running simultaneously, they compete for TCP/443; this is the same engine (Xray), but **two separate processes with different keys and different client databases**.

## 3. Fresh Installation: Three Scenarios

> **Important:** `x-ui` (3x-ui) and `xray.service` (if deploying the bot Xray without a panel) **both want TCP/443**. Only **one** of them may listen on a given VPS. The `deploy_fresh_vps.sh` script performs a pre-flight check: if port 443 is already occupied by another service, installation will be aborted.

Most operators will use **§3.1** (3x-ui only) or **§3.3** (3x-ui + bot via `/xui_setup`). **§3.2** (bot Xray without a panel) is for operators who have no need for a browser panel at all.

### 3.1 Scenario A — 3x-ui Only (Native), Bot Not Used for VLESS

Minimal steps for a fresh Debian 12 host.

#### Step 1. Host Preparation (as root)

```bash
apt-get update && apt-get upgrade -y
apt-get install -y curl ufw socat ca-certificates
ufw allow 22/tcp        # your SSH port
ufw allow 443/tcp       # VLESS-Reality
ufw allow 35421/tcp     # 3x-ui panel port (choose a non-default port, not 54321)
ufw --force enable
```

#### Step 2. Install the Panel with a Single Command

Official MHSanaei script:

```bash
bash <(curl -Ls https://raw.githubusercontent.com/MHSanaei/3x-ui/master/install.sh)
```

If you are using the shared `deploy_fresh_vps.sh`, select
**`[2] VLESS-Reality via 3x-ui + x-ui menu`** or
**`[3] VLESS-Reality via 3x-ui browser UI`** in the first dialog.
Both options run this same official installer and prepare `/opt/TelegramHelper`
for later bot deployment. The difference is only which interface you consider
primary: the `x-ui` terminal menu or the browser panel.

The script will ask for:

- **Username / Password** — web panel credentials. Write them down.
- **Panel port** — TCP port for the panel itself (e.g. `35421`). This port must be **open in UFW**, not the default `54321`.
- **Web base path** — secret path for the panel. May be a **single segment** (`myadmin`) or **multi-level** (`secret/admin/v2`). Longer and less common = harder to discover by scanners. In a URL this becomes `/<base_path>/`.

The full panel URL is: `https://<IP>:<panel_port>/<base_path>/`.
Example: `https://YOUR_VPS_IP:35421/myadmin/` (the trailing `/` is required).

Verify after installation (substitute your port):

```bash
systemctl status x-ui
ss -ltnp | grep 35421
journalctl -u x-ui -n 20 --no-pager
```

If the panel port is not 54321, update the UFW rule:

```bash
ufw delete allow 54321/tcp 2>/dev/null || true
ufw allow 35421/tcp        # substitute your port
ufw reload
```

#### Step 3. Browser: Create a VLESS-Reality Inbound

Open `https://YOUR_VPS_IP:35421/myadmin/` → **Inbounds → Add Inbound** and set:

| Field | Value |
| --- | --- |
| **Remark** | any name (e.g. `vless-reality`) |
| **Protocol** | `vless` |
| **Listen IP** | empty (= 0.0.0.0) |
| **Port** | `443` |
| **Total** | `0` (unlimited) |
| **Decryption** | `none` |
| **Flow** (client) | `xtls-rprx-vision` |
| **Transmission** | `tcp` |
| **Security** | `reality` |
| **uTLS** | `chrome` (or `firefox`) |
| **Dest** | `yahoo.com:443` (bot default; `www.microsoft.com` is aggressively filtered by some mobile ISPs) |
| **Server names (SNI)** | `yahoo.com` |
| **Private/Public Key** | click **Get New Cert** — the panel generates the key pair |
| **Short IDs** | click **+** — add a pair of random values |
| **Clients** | add at least one: name (email), UUID can be generated with the button |

Save. In the inbound list, click **QR / URL** next to the client — this is the working `vless://...` link.

#### Step 4. Verify Native 3x-ui

```bash
systemctl status x-ui                  # should be active (running)
ss -ltnp | grep -E ':(443|54321)\b'    # 443 = panel Xray, 54321 = panel UI
journalctl -u x-ui -n 50 --no-pager    # no errors
```

In a client (Clash Meta or any VLESS client), import the `vless://` link → connect → verify the external IP.

> The bot is **not used for VLESS** in this scenario. If you want to create clients and deliver QR codes directly from Telegram without opening a browser, see **§3.3** (`/xui_setup`). The `/vless_*` commands here are **irrelevant**: they edit only the bot's local JSON and have no relation to the running panel Xray.

### 3.2 Scenario B — Bot Xray on Host Only, Without 3x-ui

This option is for operators who **do not need a browser panel** and prefer Telegram-only management. The bot sets up a native `xray.service` via a ready-made script. **3x-ui is not needed in this scenario.**

#### Step 1. Upload `deploy_fresh_vps.sh` to the VPS and Run It

From your local machine:

```bash
scp -P YOUR_SSH_PORT deploy_fresh_vps.sh root@YOUR_VPS_IP:/root/
ssh -p YOUR_SSH_PORT root@YOUR_VPS_IP
```

On the VPS:

```bash
chmod +x /root/deploy_fresh_vps.sh
bash /root/deploy_fresh_vps.sh
```

The script is interactive: select **`[1] VLESS-Reality legacy xray.service`**, and optionally **`[3] telegram-helper + dockhand`** in the container deployment menu. It will automatically:

- install swap and system packages;
- install **Docker** and a native **`xray.service`** on :443;
- generate a UUID, Reality keys, and a short_id, writing them to both `/usr/local/etc/xray/config.json` and `/opt/TelegramHelper/vless_config.json`;
- create the `/opt/TelegramHelper/` directory and empty JSON files;
- save everything to `/opt/TelegramHelper/CREDENTIALS.txt` on completion.

#### Step 2. Deploy Bot Code and `.env` (from Local Machine)

```bash
cd /path/to/TelegramHelper
cp example.env .env.deploy && nano .env.deploy   # fill in TELEGRAM_BOT_TOKEN, ADMIN_IDS

rsync -avz -e 'ssh -p YOUR_SSH_PORT' \
  --exclude 'venv' --exclude '__pycache__' --exclude '.env' \
  --exclude 'app_keys.json' --exclude 'users.json' --exclude '*.log' \
  --exclude '.git' ./ root@YOUR_VPS_IP:/opt/TelegramHelper/

scp -P YOUR_SSH_PORT .env.deploy root@YOUR_VPS_IP:/opt/TelegramHelper/.env
ssh -p YOUR_SSH_PORT root@YOUR_VPS_IP 'cd /opt/TelegramHelper && docker compose up -d --build telegram-helper'
```

After the container starts, open the bot in Telegram.

#### Step 3. Bot Commands for VLESS

All commands are available to admin/special users.

| Goal | Bot Command |
| --- | --- |
| **Understand current state** (JSON vs host) | `/vless_status`, `/diag` |
| **Pull `server`/`public_key`/`short_id` from host Xray** (already done after `deploy_fresh_vps.sh`, but useful after manual edits) | `/vless_sync` |
| **Set the public server address** (if the field is empty) | `/vless_set_server <IP_or_domain>` |
| **Generate a new Reality key pair** (from scratch, without Xray) | `/vless_gen_keys` |
| **Change SNI / fingerprint / port / short_id** | `/vless_set_sni`, `/vless_set_fingerprint`, `/vless_set_port`, `/vless_set_shortid` |
| **Create a bot-managed profile for a Telegram ID** | `/provision <telegram_user_id>` |
| **View / re-deliver URI and QR** | `/profiles <telegram_user_id>` |
| **User retrieves their own profile** | `/my_profile` |
| **View/add/delete clients manually** | `/vless_list_clients`, `/vless_add_client <name>`, `/vless_del_client <name>` |
| **Get QR / link for a client manually** | `/vless_qr <name>` or `/user <id>` card → button |
| **Toggle the `enabled` flag in JSON** | `/vless_on`, `/vless_off` |
| **Full client config export** | `/vless_export` |
| **Self-diagnostics** | `/vless_test` |

> **Important:** for legacy VLESS the primary user delivery path is now the same as for 3x-ui: `/provision` → `/profiles` → `/my_profile` or `/email_profile`. These commands create a canonical client in `vless_config.json`, apply it to `/usr/local/etc/xray/config.json`, and restart `xray.service`. The `/vless_*` commands are for manual diagnostics and targeted admin operations.

#### VLESS-Reality Fine-Tuning Glossary

`Reality` — an Xray masking mode in which a VLESS connection looks like a regular TLS visit to a public website. The server does not need a real certificate for your domain: the disguise is built around a Reality key pair, SNI, a short ID, and the chosen `dest`.

`SNI` / `serverName` — the domain name the client presents in the TLS ClientHello. To DPI it looks like the target of an ordinary HTTPS connection. The bot and install scripts default to `yahoo.com`. The previous default was `www.microsoft.com`, but that is the most common SNI in VPN guides and is filtered by some mobile ISPs even before Xray (see the troubleshooting section below). Any large public domain works (`yahoo.com`, `www.cloudflare.com`, `www.apple.com`). SNI must be consistent with `dest` and the inbound settings.

`dest` — the real external address Xray impersonates during the TLS handshake, e.g. `yahoo.com:443`. In 3x-ui this field is usually called `Dest`. In legacy `xray.service` it lives in the Reality settings of the server-side config. If `dest` is unreachable or looks suspicious, the Reality profile may pass DPI less reliably.

`public_key` / `private_key` (`pbk`) — the Reality key pair. The `private_key` stays on the server only; the `public_key` is included in the client URI as `pbk`. Generating a new pair invalidates all existing clients until they receive a new profile.

`short_id` (`sid`) — a short Reality client/handshake identifier added to the URI as `sid`. An inbound may have multiple short IDs. Changing `short_id` can break old URIs that carry the previous `sid`.

`fingerprint` (`fp`) — the uTLS fingerprint: `chrome`, `firefox`, `safari`, `ios`, `android`, etc. It controls how closely the TLS ClientHello resembles a real browser or platform. The default is typically `chrome`; changing it is only worthwhile for A/B testing on a specific network.

`flow` — the VLESS/XTLS mode. `xtls-rprx-vision` is standard for Reality. Do not change `flow` unless you know whether your client supports it.

`transport` / `network` — the VLESS transport inside Xray. This guide uses `tcp` + `security: reality` as the baseline. gRPC/WebSocket/XHTTP are separate transport models, not a simple checkbox on the current legacy flow.

`port` — the public TCP port for VLESS-Reality on the VPS, usually `443/tcp`. If you move VLESS to a non-standard port, open the firewall and re-export all profiles.

`uuid` — the VLESS client identifier. It is not a password in the classical sense, but it is a secret credential. In bot-managed flow a UUID is created for each client; the shared Reality fields (`pbk`, `sid`, `sni`, `fp`, `flow`) remain the same across all clients within an inbound.

A practical rule for DPI research: change **one parameter at a time**. After changing `sni`, `fingerprint`, `short_id`, `public_key`, `port`, or `flow`, re-issue URI/QR via `/profiles`, `/my_profile`, or `/vless_export`; otherwise the client will keep using the old profile.

### 3.3.0 Mesh-Only Panel (Tailscale/Headscale)

If the 3x-ui panel is bound **only** to the host's mesh IP (e.g.
`https://100.64.0.6:8081/myadmin`) and is not publicly reachable, the bot in
the default Docker bridge **will not see the mesh interface**. When you enter
such a URL in `/xui_setup`, the bot will detect the CGNAT prefix
(100.64.0.0/10) and provide specific steps at the login stage. The short
answer — what to do:

```bash
cd /opt/TelegramHelper
docker compose \
  -f compose.yaml \
  -f compose.host.yaml \
  up -d --force-recreate
```

The override file `compose.host.yaml` (included in the repository) switches
`telegram-helper` to `network_mode: host` and sets
`telegram-helper:host-gateway` for Dockhand — the existing
`DOCKHAND_API_URL=http://telegram-helper:8000` continues to work.
After rebuilding, `/xui_setup` with a mesh URL will proceed without conflicts.
To return to bridge mode, simply run without `-f compose.host.yaml`.

Details and rationale for each override are in the comments of the file itself.

### 3.3 Scenario C — 3x-ui + Bot as a Telegram Front-End (`/xui_setup`)

The most convenient option if you already have a native 3x-ui from §3.1 and
want to deliver QR codes and links to clients **directly from Telegram**, without
opening a browser every time. **The single source of truth remains 3x-ui**;
the bot calls its REST API.

#### Architecture: One Inbound, Two Client "Types"

After this variant, the bot **does not create a separate inbound**. Everything lives in one manual inbound on :443 (`default_inbound_id` from `/xui_setup`). Isolation between the admin's manual clients and bot-managed clients is **by name**:

| Client type | Where it lives | Names | Who writes it |
| --- | --- | --- | --- |
| **Manual** (admin) | manual inbound, e.g. `vless-reality` on :443 | arbitrary (`iPhone13`, `iPad-Work`, …) | admin in the 3x-ui browser |
| **Bot-managed** | same inbound | canonical `<Prefix>_ID<first2>_<last2>` (regex `^(Vless\|Hys\|Mtp\|...)_ID\d{2}_\d{2}$`) | bot via `/provision` / `/clean_user` |

Benefits:

- **Full stealth**: bot-managed clients on :443 alongside manual ones; Reality handshake to `yahoo.com` disguises both. DPI cannot distinguish them. No non-standard ports in `ss -tlnp`, no extra firewall rules.
- **Shared Reality keys**: `pbk`, `sid`, `sni`, `fp`, `flow` — the same as the admin's manual clients. The bot does not duplicate settings.
- **Isolation**: the bot **does not touch** manual clients with arbitrary names — `clean_user` / `provision` filter by canonical regex and only add/remove those. `iPhone13` in the inbound will always be safe.

> **If you tested the old Variant A** (separate inbound on port 444): after switching, the old inbound remains in the panel as an orphan. At the next `/provision`, the bot will migrate canonical clients from there to the default inbound (`dup-email sweep`). Remove the orphan inbound manually in the panel when convenient — it is no longer used.

#### Step-by-Step Scenario (with real commands)

##### A) One-Time — Integration Setup (performed by admin)

1. Make sure 3x-ui is running per §3.1 and already has a Reality inbound (manual).
2. Start the bot in Docker (`/opt/TelegramHelper`). It will not install its own `xray.service` — 443 is taken by the panel, and the pre-flight check in the script detects this.
3. In Telegram, from the admin account:

   ```text
   /xui_setup
   ```

   The bot leads a step-by-step dialog:

   | Step | Bot prompt | What to enter |
   | --- | --- | --- |
   | 1 | Panel URL | e.g. `https://YOUR_VPS_IP:35421/myadmin/` (trailing `/` required) |
   | 2 | Panel login | `username` from 3x-ui (NOT the webBasePath) |
   | 3 | Panel password | the bot **deletes the message from the chat immediately**; on disk the password is stored encrypted with `ENCRYPTION_KEY` |
   | 4 | Verify TLS | for self-signed (typical for 3x-ui on an IP) — select "🔓 self-signed" |
   | 5 | Inbound selection | the bot shows the panel's inbound list; select the VLESS-Reality one (it becomes `default_inbound_id` — the source for cloning) |

4. Verify the integration:

   ```text
   /xui_status         # "✅ integration enabled", shows base_url and default_inbound_id
   /xui_list           # all panel inbounds (informational)
   ```

   Integration management commands: `/xui_set_inbound <id>` (change the default inbound — bot-managed clients will migrate automatically at the next `/provision`), `/xui_enable` / `/xui_disable` (temporarily disable integration while keeping credentials), `/xui_clear` (completely erase credentials, requires confirmation `YES`).

##### B) Per-User — Profile Delivery (performed by admin)

1. Grant the target Telegram account the "special" role:

   ```text
   /special_add <telegram_id>
   ```

   Without this, profile delivery is blocked by the bot's policy (admin/special only).

2. Create a profile with one command (recommended path):

   ```text
   /provision <telegram_id>
   ```

   - The bot adds a client **directly to `default_inbound`** (manual VLESS, typically on :443) with email = canonical name `<Prefix>_ID<first2>_<last2>` (for Telegram ID `8288584609` this is `Vless_ID82_09`).
   - The new client shares the same Reality keys as the manual ones — Reality is identical for the entire inbound. No new ports, no extra firewall rules.
   - The bot immediately builds and returns a `vless://` URI + QR image.
   - **15-minute TTL** on the URL and QR message in the chat — the working link does not persist forever. After `/provision`, the admin has 15 minutes to forward it to the user or copy the QR; then the bot deletes the messages. Repeating `/provision` is fine — there is no counter for admins.
   - **Self-heal**: if a duplicate client with this email exists in some other inbound (e.g. from an old Variant A setup or manual tests), the bot will automatically find and delete it, then retry the add. Migration happens transparently.

   Alternative — admin picker:

   ```text
   /provision               # without argument → inline keyboard
                            # listing all admin/special users
   ```

   Batch mode:

   ```text
   /provision_all           # for all admin + special users at once
   ```

3. View/re-deliver an already-created profile:

   ```text
   /profiles <telegram_id>
   /profiles                # without argument → admin picker
   ```

   Returns text with the canonical name + URL, plus a QR image. No side effects — read-only.

4. Send the finished profile by email:

   ```text
   /setemail <telegram_id> user@example.com   # bind email once
   /email_profile <telegram_id>               # send URL+QR to the bound address
   /email_profile <telegram_id> other@example.com  # or a one-off address
   ```

   `.ru`/`.su` recipients are blocked by default (`SMTP_BLOCKED_TLDS`) — outbound SMTP to those zones from non-Russian VPS is unreliable. SMTP is configured in `.env` (see `example.env`).

5. Delete a bot-managed client (e.g. for rotation):

   ```text
   /clean_user <telegram_id> YES
   /clean_user                # without argument → admin picker (click = confirmation)
   ```

   Deletes **only** canonically named clients in the default inbound (the bot filters by regex `^(Vless|Hys|Mtp|Tuic|Any|Xh)_ID\d{2}_\d{2}$`). Manual clients with arbitrary names are not touched. If a canonical client with the same name exists in a legacy inbound from the old Variant A, it will be removed as well.

##### C) Self-Service — User Retrieves Their Own Profile

1. After steps B1–B2, the special user in **their own private chat** with the bot runs:

   ```text
   /my_profile
   ```

   The bot returns:
   - a short summary with the canonical profile name;
   - **separate** messages with the URL for each enabled protocol (tap on a `<code>` block to copy on iOS / long-tap → Copy on Android);
   - a QR image for each protocol (for scanning with the client camera).

   **Security:**
   - All these messages **auto-delete after 15 minutes** (via `asyncio.create_task` with `bot.delete_message`).
   - **Limit of 3 successful views.** On the 4th call to `/my_profile`, the bot: deletes all output from the chat + removes canonical clients from the bot-managed inbound + sends an **HTML notification to admins** "auto-cleanup, reason: view limit reached".
   - The counter resets on the next `/provision <uid>` or `/clean_user <uid> YES`.

   See `SECURITY.md` (§ "QR, URI, and bot-managed profiles") for details.

##### D) What NOT to Do in Scenario C

After Setup all legacy `/vless_*` commands that could corrupt the state **return a redirect message** when integration is active:

- `/vless_set_*` (server, port, uuid, key, shortid, sni, fingerprint), `/vless_gen_keys`, `/vless_reset` → "configure the inbound directly in the panel" (3x-ui URL).
- `/vless_add_client`, `/vless_del_client`, `/vless_qr` → "use /provision / /clean_user / /email_profile / /my_profile".
- `/vless_on`, `/vless_off`, `/vless_test`, `/vless_sync` → "the real Xray is run by 3x-ui, manage it via the panel".

It is no longer possible to accidentally "go to the wrong place" with a legacy command in Scenario C.

`/vless_status` and `/vless_export` now first show a **3x-ui overview** (panel URL, both inbounds with client counts, navigation to `/provision`/`/profiles`), followed by the old local `vless_config.json` block marked "not in use".

`/vless_list_clients` in Scenario C shows **bot-managed clients** (canonical names in the bot inbound). The manual inbound with hand-created clients is not touched — the admin manages it directly in the panel.

##### E) Rotation / Deletion

- **Delete bot-managed clients:** `/clean_user <id> YES` (or a click in the picker) — removes canonical clients (`Vless_ID*_*`, `Hys_ID*_*`, …) from the default inbound for that user across **all** enabled protocols. Manual clients are not touched.
- **Rotate UUID** (secret rotation): `/clean_user <id> YES` + `/provision <id>` — UUID and subId are regenerated. The canonical name stays the same.
- **Delete a manual client from the manual inbound**: only via the 3x-ui browser panel. The bot does not write to it.

If a client fails to connect, common causes:

- In Scenario B: `server` in `vless_config.json` is not a public IP/domain → fix with `/vless_set_server` or `/vless_sync`.
- In Scenarios A/C: the link was taken **not from the panel/bot-managed**, but from an old bot `/vless_qr` — its UUID/`pbk` do not match what the running Xray knows. Re-issue via `/provision <id>` or take it directly from the panel.
- **UFW** is blocking 443 → `ufw status | grep 443`.
- Another service (old nginx, a second Xray) is accidentally occupying **443** → `ss -ltnp | grep 443`, stop the extra service.
- Windows + TUN: Clash Meta must be run **as administrator**, otherwise `utun` will not open. For testing, switch to SOCKS5/Auto.

### 4.4 Reference: DNS Inside the Tunnel (sing-box / Xray Client)

**What this means:** DNS queries (name resolution) go **through the VPN/proxy** (along with other traffic) rather than bypassing it directly to the ISP's DNS from the physical interface. This matters for leaks: the external IP is already "the VPS IP", but DNS may still reveal your home ISP's resolvers if the client does not intercept and route DNS through the tunnel.

**Where to configure this:** on the **user's device**, in the client application (Clash Meta, sing-box, Hiddify, v2rayN, etc.). The Xray config **on the VPS** (3x-ui or the bot's `xray.service`) only describes the inbound; it **does not replace** the local DNS stack on the phone/PC.

#### Checking the Client Config (sing-box)

If the client generates a **sing-box** config (e.g. Clash Meta / sing-box in TUN mode):

1. Open the generated JSON.
2. Ensure there is a **`dns`** block with servers (e.g. public `8.8.8.8` / `1.1.1.1`).
3. In **`route.rules`** there should be a rule for **`protocol: dns`** with action **`hijack-dns`** (current sing-box) or a route to a separate **`dns-out`** outbound (older variant). This means: DNS intercepted by the sing-box core is handled **inside** the stack and does not bypass the tunnel.

#### Practical Verification

1. **Extended DNS leak test**
   Connect VPN/TUN, open e.g. [https://dnsleaktest.com](https://dnsleaktest.com) → **Extended test**.
   - If DNS goes inside the tunnel through your VPS: the list will typically show resolvers **in the VPS country/provider** or chosen public DNS, but **not** resolvers exclusive to your home ISP.
   - If only home ISP servers appear with VPN on — DNS interception is not working as expected.

2. **Compare VPN on / off**
   The same test with VPN disabled vs enabled: the set of DNS servers displayed should **differ significantly** (unless you have a deliberate split-tunnel policy).

3. **sing-box log**
   At **debug** log level, the log file (from the `log` section) shows whether DNS is being processed and where requests go.

## 5. Why Clients and Profiles Are Not "Auto-Synced"

This only matters if you have **deliberately run both Xray instances simultaneously** (3x-ui + bot `xray.service`). In a normal configuration (any of §3.1–§3.3), this situation should not arise.

1. **Different processes and files.** The bot's Xray reads one `config.json`; the panel's Xray reads its own. They do not share databases.
2. **Different sources of truth.** UUIDs and client names in `vless_config.json` do not flow into `x-ui.db` automatically and vice versa.
3. **Port 443.** If both try to listen on TCP/443, only one process wins; the other will fail to start — this is a conflict, not a merge.

The bot's message is accurate:

> *3x-ui detected on VPS. The bot writes VLESS clients to its own `/usr/local/etc/xray`; 3x-ui writes to its own `/etc/x-ui/x-ui.db`. Bot clients and 3x-ui clients do not overlap.*

"Do not overlap" = **no shared automatic client list**. Manually creating identical parameters in two places is allowed but requires manual synchronization.

## 8. FAQ

**The client keeps dropping with `EOF` on every connection, even though the config (UUID, public key, shortId, SNI, flow) exactly matches the server — what is wrong?**
Most likely the **clock on the client device has drifted**. VLESS-Reality embeds a timestamp in the TLS handshake, and the server rejects authentication outside a narrow window. With a drifted clock, TCP to the server is established but Reality transparently falls through to the real `dest` (e.g. `yahoo.com`), which closes the "garbage" stream — the client sees `EOF`. A server-side indicator: `xray x25519 -i=<privateKey>` yields exactly the public key in the profile and everything matches, yet the connection still drops. How to check and fix:

```bash
# Windows (cmd as administrator):
w32tm /query /status          # "Source: Local CMOS Clock" / "not synchronized" = problem
net stop w32time & net start w32time & w32tm /resync /force

# macOS:
sntp -t 4 time.apple.com       # shows offset; large skew = problem
sudo sntp -sS time.apple.com   # or enable network time in System Settings
```

**ALL clients drop with `EOF`; the Xray log shows `REALITY: processed invalid connection` even with correct keys and even over loopback on the server itself?**
The cause is a **`::/0 → blackhole`** rule in the `routing` section of the Xray config (added as a workaround for "no IPv6 egress"). Reality must reach `dest` (`serverNames[0]:443`) on every connection to deliver a real TLS certificate. When `dest` (e.g. `yahoo.com`) resolves to **IPv6**, this call hits the `::/0` blackhole → the relay cannot complete → Xray rejects **every** client as `invalid connection`. The fix (already applied in the generator — see `vless_manager.export_xray_config`): **remove the `::/0` blackhole** and suppress missing IPv6 egress via `freedom/UseIPv4` + `sniffing destOverride` on the inbound. For **existing servers** deployed before the fix, regenerate the config:

```bash
cd /opt/TelegramHelper && git pull
python3 scripts/sync_xray_config.py
xray -test -config /usr/local/etc/xray/config.json && systemctl restart xray
jq '.routing? // "no routing (ok)"' /usr/local/etc/xray/config.json   # should have no ::/0
```

**The server is healthy, keys/port/SNI match in the link, the port is confirmed open from the hosting panel and an external scanner, yet the client simply will not connect over mobile data (works fine on Wi-Fi or from another VPS) — what to do?**
This is almost certainly **active DPI filtering by the mobile ISP**, not a config bug. The port and IP may be fully reachable (an external scanner and even `curl`/a browser over mobile data will show a certificate warning — meaning TLS reached Xray), yet DPI still cuts the Reality pattern. The confirmed culprit is the **SNI**: common VPN-guide domains (`www.microsoft.com` in particular) are already in some carriers' fingerprint lists — switching to a less "typical" `sni` (e.g. `yahoo.com`) on the same server/port/keys has resolved the problem immediately.

Diagnostic steps:

1. Compare `pbk`/`sid`/`port`/`flow`/`fp` in the link with what is actually in `/usr/local/etc/xray/config.json` (`xray x25519 -i "$PRIVATE_KEY"` must produce the same `pbk` as in the link/QR).
2. Run `journalctl -u xray -f` and try to connect over mobile data — if nothing appears in the log, traffic never reached the server — this is a Reality filtering signature (a config bug, by contrast, would produce an error in the log).
3. Compare with another server where things work — often the only difference is `sni`.
4. Change the SNI most easily with the buttons: send `/vless_set_sni` **without a domain** — the bot shows a list of presets (the current one is marked ✅). One tap changes `sni`, rewrites `/usr/local/etc/xray/config.json`, and offers a "🔄 Restart Xray" button. Then regenerate QR/link (`/vless_qr <name>`, `/profiles <id>`, or `/my_profile`) — old links with a different `sni` are no longer valid. To set a custom domain: `/vless_set_sni example.com`. Manually on the VPS:
   `sed -i 's/www\.microsoft\.com/yahoo.com/g' /usr/local/etc/xray/config.json`
   → `xray -test -config /usr/local/etc/xray/config.json` → `systemctl restart xray`.

Changing the port is not needed (Xray itself warns at startup: *"Listening on non-443 ports may get your IP blocked by the GFW"*) — the root cause was the `sni`, not the port. See also `AVAILABLE_SNI` in `vless_manager.py`.

> 💡 **QR code directly in the VPS terminal.** The `qrencode` package is installed automatically by the deploy scripts. It renders a QR code for the link directly in the SSH console so it can be scanned by a phone without the risk of copy-paste errors:
>
> ```bash
> printf '%s' "$VLESS_LINK" | qrencode -t ANSIUTF8
> ```
>
> If the package is missing: `apt-get install -y qrencode`.

**Does the bot have its own web panel?**
No. The bot has **only a Telegram interface** (`/vless_*`, `/xui_*`, `/provision`, `/profiles`, `/user`, QR commands). The only web panel in the system is 3x-ui (if you installed it).

**I ran `/vless_add_client name` and the bot replied "🛑 Client management goes through the bot-managed flow".**
This is correct behavior in Scenario C (when `/xui_setup` is configured). After Setup, all legacy `/vless_*` commands are guarded and return a redirect to prevent accidentally writing to the inactive `vless_config.json`. Use `/provision <user_id>` to create, `/clean_user <user_id> YES` to delete, and `/profiles <user_id>` to view.

**I created a client in an older bot version via `/vless_add_client`; the link does not work.**
These are "stale records" from past sessions, before Scenario C was enabled. The server (the 3x-ui panel's running Xray) does not know about these UUIDs. In Scenario C, `/my_profile` retrieves the link from the default inbound of the panel and ignores old legacy entries in `vless_config.json`. The entries can be cleaned manually: `cat /opt/TelegramHelper/vless_config.json | jq '.clients'` to inspect; to delete — edit the file directly (`/vless_del_client` is guarded in Scenario C).

**Where do bot-managed clients go after Variant B?**
Into the same inbound on :443 as the admin's manual clients. Reality keys are the same for both types (all in one inbound), full Reality stealth applies. Isolation is by name: the bot only touches clients matching the canonical regex `^(Vless|Hys|Mtp|Tuic|Any|Xh)_ID\d{2}_\d{2}$`. Manual clients like `iPhone13` or `MacBook-Air` are not considered "owned" by the bot and will not be modified.

**A special user complains: "got `/my_profile`, then again, then — the profile disappeared".**
This is by design. **Limit of 3 successful `/my_profile` views**: on the 4th call the bot removes canonical clients from the default inbound and notifies admins. To re-issue — `/provision <id>` (resets the counter). See `SECURITY.md` (§ "Ephemeral keys and URLs") for details.

**Does the admin's URL and QR after `/provision` persist indefinitely?**
No. The **15-minute TTL for the admin flow** was added: messages with URL/QR from `/provision <id>` and `/profiles <id>` (including inline pickers) also **auto-delete after 15 minutes**. There is no view counter for admins — you can repeat as many times as you like, but URLs do not accumulate in the chat.

**`/email_profile` replies "email rejected: .ru domain is blocked".**
By default `SMTP_BLOCKED_TLDS=.ru,.su` — outbound SMTP to those zones is unreliable from a non-Russian VPS, and `/email_profile` blocks those recipients preemptively. Solutions: (a) use an international address (gmail/proton/outlook); (b) if the user insists — edit `SMTP_BLOCKED_TLDS=` (empty string = allow all) in `.env` and rebuild the container.

**I installed the bot with its own Xray; now I want to switch to 3x-ui (or vice versa).**
First stop the old stack:

- bot Xray → `systemctl stop xray && systemctl disable xray`;
- 3x-ui → `systemctl stop x-ui && /usr/local/x-ui/x-ui uninstall`
  (or `docker compose down` for the container).

Then bring up the new one per §3.1 (3x-ui only), §3.2 (bot only), or §3.3 (3x-ui + bot via `/xui_setup`).
